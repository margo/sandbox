# MIAF Design Rationale and Current Trade-offs

This document explains selected implementation decisions made by the Margo Code First Sandbox for its Margo Identity and Authorization Framework (MIAF) support. It is intended to clarify why the current design was chosen, rather than to define a normative MIAF requirement. The choices reflect the specification and lifecycle workflows available when the implementation was developed. As MIAF evolves and automated enrollment, renewal, reissuance, and revocation workflows become better defined, these choices may be revised or optimized.

## MIS SVID Minting Interface and Unix Socket

MIAF does not currently define an operator-facing procedure or API for minting SVIDs. The sandbox therefore needed a practical way to provision identity material while keeping the workflow usable for operators. SPIRE's facilities for manually generating SVIDs provided a useful point of reference, and a CLI was selected as the interface. A command-line workflow is straightforward to invoke interactively and to automate in scripts, which is useful for sandbox setup and interoperability events such as Plugfests. It also fits the current operator-driven lifecycle, where identities are provisioned out of band rather than issued through an automated enrollment protocol.

The minting operation currently produces both an X.509 certificate and its corresponding private key. Because that is sensitive material, the sandbox exposes the operation through a local Unix domain socket rather than a network listener. This keeps the minting API local to the host and avoids making a certificate-and-key issuance endpoint remotely reachable as part of the current design. Socket ownership and filesystem permissions remain important parts of that local security boundary.

This is a pragmatic interim interface, not a claim that Unix sockets are the eventual MIAF interface. Once MIAF specifies automated enrollment, authorization, renewal, revocation, and related lifecycle operations, MIS can adopt an interface aligned with those workflows and their security requirements.

## Disabling HTTP Keep-Alive Connections

The MIAF model assigns each peer that verifies another peer the role of a verifier, and expects the verifier to apply its local authorization policy. In the sandbox, the WFM can apply its device-client authorization policy in server-side middleware, so it can evaluate that policy for incoming requests. The WFM client has a different constraint: it validates the WFM's identity and local authorization policy using the peer certificate presented during TLS negotiation.

TLS peer certificates are associated with a connection, not with each HTTP request. When an HTTP client reuses a keep-alive connection, subsequent requests do not perform a new TLS handshake and do not receive a newly presented peer certificate. That can delay when a client observes a changed server identity or policy decision, particularly if the client changes WFM endpoints over its lifetime. The sandbox expects a device agent to be paired with one WFM at a time, while still allowing that pairing to change; retaining a connection indefinitely is therefore not a good basis for applying current policy to the selected WFM.

The sandbox disables keep-alive reuse so that each request establishes a new connection and reaches the TLS verification path again. This favors timely enforcement of the client's local authorization policy over connection efficiency. The cost is additional connection setup and TLS-handshake work, which can increase request latency and resource use. MIAF describes keeping connection lifetime well below relevant trust-bundle refresh intervals or SVID expiration; the sandbox currently takes the stricter approach of not reusing HTTP connections, rather than selecting and tuning a keep-alive lifetime. This choice is intended to make the policy boundary straightforward under the current operator-driven lifecycle, and may be revisited as lifecycle automation and connection-management guidance mature.

## Enforcing Client-Side Authorization During TLS Verification

For a WFM client verifying a WFM server, the sandbox performs local authorization as part of TLS peer verification. The client receives the server's certificate during the TLS handshake, so it can validate the SVID and evaluate the peer identity against its local authorization policy before allowing the connection to be used for application requests.

This placement is deliberate. Server-side request middleware can inspect a verified client identity on each request, but a client making requests does not have an equivalent per-request middleware point at which a newly presented server certificate is available: the certificate is presented when the connection is established. With keep-alive reuse, later requests also have no new handshake at which to evaluate a changed certificate or policy. A WFM client may connect to a different WFM over time, so its decision needs to be made against the identity presented for that connection rather than implicitly trusting a previously established connection.

Coupling SVID verification and the client's local authorization check to TLS establishment keeps the decision at the point where the peer identity becomes available. The client does not send application traffic unless the certificate validates and the peer identity satisfies local policy. This is a simple, fail-closed boundary that limits the chance of requests being sent over a connection to an unauthorized peer. The sandbox uses server-side middleware where that is the appropriate enforcement point, and handshake-time verification for the client-side decision; these mechanisms address different directions of the mTLS relationship.

The design is intentionally conservative and has a performance cost when combined with disabled keep-alive reuse. As MIAF clarifies identity lifecycle automation and connection-lifetime expectations, the sandbox may adopt a more efficient approach, provided it preserves timely policy updates and authorization before application traffic is accepted.
